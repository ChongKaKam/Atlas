# Review 与 Apply

Review-first 要求变更能被理解和审阅，不要求每次小改动都增加一轮确认。

## 何时应用

- 用户只要求建议、计划、ASK 或 AUDIT：只读目标库。可以在明确的临时工作目录准备草案，但不得把建议当成正式结论写入。
- 用户明确要求新增、整合、修改、执行一个已给出的计划：有相应写入授权。先检查已有内容与差异，落实授权范围内的改动，展示结果。
- 用户要求“先让我 review”：准备完整草案和 diff，等待其批准后应用。
- 用户没有给出冲突取舍所需信息：先完成独立部分，并列保存有证据的分歧；不要替用户选择项目决策、丢弃原始实验数据或扩大删除范围。
- 批准过的计划继续有效。目标文件在批准之后发生改变时，重新读取差异，保留新修改；如果新内容实质改变计划，再提出具体决定。

## 可审阅变更的最小内容

多文件整合计划列出 KU 的问题、上下文、来源、已有候选、动作、目标路径与原因。对 Skip 指明是无新增价值，还是本轮范围内暂缓。新标签、状态变化、纠错和移动均可见。

有 Git 时先看目标文件的 `git status --short` 和现有 diff。检查时使用正确的知识库路径，避免把上层项目误当作独立知识库。不 stage、不 commit；新文件需读取或以 `git diff --no-index /dev/null <file>` 展示，普通 `git diff` 不包含它们。非 Git 目录在临时目录保存所需文件的原样副本，使用 `diff -u` 对比；不要建立强制备份数据库。

## Apply 顺序

1. 重读要改的原文件，确认预期内容仍在，检查链接和已有用户编辑。
2. 新增/改写知识内容，保留来源定位、版本/环境与不确定性。修改工具使用可定点应用的编辑方式。
3. 移动文件时同时修复 inbound 和 moved-file outbound relative links、图片链接、引用式链接；重命名标题时还须检查 heading anchors。
4. 实质改动更新 `updated`，保留原 `created`。拆分得到的新文件使用当天创建日期；合并到既有文件保留该文件的创建日期。来源历史放正文。
5. 执行相关工具检查，比较之前与之后的问题；不要因为库中旧问题存在就修复授权外的全部文件。
6. 自审语义：来源是否支撑结论、是否把上下文差异当成冲突、是否存在丢失的 KU。报告新增问题、旧问题和未完成的检查。

应用中途出错时报告具体已写入文件；不要声称事务性回滚，也不要用重置命令撤销用户改动。删除原文件仅在内容完整迁移、链接修复、删除明确在授权范围内之后执行。
